# v0.3.1-beta — what the first Linux run found

A patch release. No behaviour changes, no new features: `v0.3.0-beta` does not
build on a clean Linux checkout, and this is the tag that does.

Both failures had the same shape — code that is correct, an environment this
project had never actually run it in, and a developer machine generous enough
to hide the difference. Neither reproduces on Windows even deliberately.

## 1. Six of seven native harnesses would not compile

```
error: implicit declaration of function 'clock_gettime' [-Werror=implicit-function-declaration]
error: 'CLOCK_MONOTONIC' undeclared (first use in this function)
```

`clock_gettime` is POSIX, not ISO C. Under `-std=c11` glibc exposes only the ISO
surface, so the declaration disappears and `-Werror` turns the implicit one into
a build failure. newlib — which both ESP toolchains use — and MSYS2's UCRT
expose it regardless. That is the whole reason this built clean on a Windows
laptop, on xtensa and on riscv32, and died only on the runner.

This was the second occurrence. `1d22d9f` fixed it in Etap 0 by adding the
feature macro to `mem_probe.c`, in that one source file; every harness written
since re-created the bug. The macro now lives in the shared GNU flag list in
`tools/host-cc.mjs`, so a new harness cannot forget it.

Only `arq_selftest.c` survived the run — not by design, but because it is the
one harness with no wall clock in it, having replaced its timing with
caller-supplied timestamps.

## 2. Three host tests cancelled, not failed

```
error: 'Promise resolution is still pending but the event loop has already resolved'
```

The Bridge health poll's timeout timer was `unref`'d, on the reasoning that a
health poll should never hold the process open. But while a reply is
outstanding that timer is the *only* thing keeping the loop alive: on the runner
it drained, and the await never returned. Removing the `unref` costs nothing —
the timer is cleared on every completion path — and turns the timeout from
"fires if the process happens to still be busy" into a guarantee.

## 3. A budget with six bytes of headroom

CI measured `size.frag.text.riscv32` at 1018 B against a 1024 B budget. It
passed, and that pass meant nothing: six bytes is inside the noise of a compiler
version bump, so the next edit to `frag.c` — or no edit at all, just a newer
runner image — would have turned the build red for a reason unrelated to
anything anybody did. Raised to 1280 B in its own `chore(budget)` commit, with
the reasoning recorded there.

## The lesson worth keeping

Both bugs were in the *first* place this code met a real Linux toolchain, and
both were invisible to a full local run — `pnpm -r test`, seven ASAN harnesses,
three ABIs, 233 metrics, all green. A green local run says the code works here.
It does not say the code works. The two CI jobs are not a formality on top of
that; for anything touching libc or the event loop they are the only
measurement that exists.
