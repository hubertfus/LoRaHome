# v0.4.1-beta — what the first CI run of Etap 3 found

A patch release over `v0.4.0-beta`. No behaviour changes, no new features: that
tag does not get through its own metric gate on CI, and this one does.

Everything the stage actually builds was green on the first run — 13 native
harnesses under **ASAN+UBSAN**, 80/80 Unity cases, 3/3 ABIs, 101 protocol tests,
every budget, and both of the gates added in T3.5 and T3.6. The build failed on
the last step of the last job:

```
REGRESSION      chaos.suite.runtime.s: 2.2 -> 3.2 (45.5% worse)
REJECTED: 1 regression(s) over 5% without a REGRESSION-JUSTIFIED: block
```

## The bug

`chaos.suite.runtime.s` is the wall-clock runtime of the Etap 2 chaos suite —
code Etap 3 never touched. The developer laptop that recorded the baseline runs
it in 2.2 s; a shared CI runner vCPU takes 3.2 s. Nothing regressed.

The gate already knew the two environments were different, and said so in the
same output:

```
NOTE: baseline was recorded in a different environment —
  baseline: win32-x64, node 24.18.0, gcc 16.1.0, xtensa 8.4.0
  this run: linux-x64, node 22.23.1, gcc 13.3.0, xtensa 12.2.0
  budgets still enforced; regression checks on size.*/bench.*/mem.* skipped.
```

It suppressed regression checks on `size.*`, `bench.*` and `mem.*` — and
`chaos.suite.runtime.s` matches none of those prefixes, so a duration got
compared across machines anyway.

**Keying the rule on the metric's name was the mistake.** What decides whether
a number is comparable across machines is what it *measures*, and the unit
already says so. `isEnvironmentSensitive` now consults the unit as well: `s`,
`ms`, `us`, `ns`, `B`, `kB`, `MB`, `kB/s` and `MB/s` are properties of the
machine as much as of the code. The name prefixes are kept, because a few
metrics carry no unit at all.

This is the same failure the SLIP budget hit in `fe7e19a`, from the other
direction: a threshold that ended up policing the runner's CPU instead of the
code. That one was a budget set from the fastest machine that would ever run
it; this one is a regression check applied across machines that cannot be
compared.

## What the rule deliberately does *not* exempt

Metrics in `count`, `pct` and `targets` stay regression-checked across
environments, and that is where most real regressions show up. A dropped
assertion count, a cross-language vector count falling from 200 to 199, a
target that stopped compiling — none of those depend on the compiler, and a
toolchain change is no excuse for them moving.

Budgets remain fully enforced in every case, environment change or not. They
are absolute contracts: 2.2 s or 3.2 s, both have to fit under the limit.

## Verification

The exemption is checked in both directions, because an exemption that always
fires is not a rule:

| Case | Result |
|---|---|
| `chaos.suite.runtime.s` 2.2 → 3.2, same environment | still a regression |
| `chaos.suite.runtime.s` 2.2 → 3.2, environment changed | not reported |
| Same metric with a breached budget, environment changed | still fails |
| `count` / `pct` / `targets` regressing, environment changed | still fails |

## Metrics from the first CI run, for the record

Worth keeping because several differ usefully from the developer machine:

| Metric | Laptop | CI | Budget |
|---|---|---|---|
| `bench.scheduler.tick.max.us` | 5.2 | 22.4 | 5000 |
| `size.bme680.text.riscv32` | 3154 B | 3048 B | 4096 |
| `size.cbor.text.riscv32` | 1454 B | 1408 B | 2048 |
| `size.gpio_digital.text.riscv32` | 924 B | 902 B | 1024 |
| `test.unity.native.cases` | 80 (over several runs) | 80/80 in one | — |
| `native.sanitized_runs` | 13 (ASAN) | 13 (**ASAN+UBSAN**) | — |

Two things that only the CI run could establish:

- **UBSAN passed.** The developer machine has MSVC's ASAN, which has no
  integer-overflow checking. The 64-bit rewrites of Bosch's compensation in
  T3.3 are now validated by a sanitizer that would have flagged the signed
  overflow the original transcription contained.
- **The ESP toolchains on CI are 12.2.0, not the 8.4.0 used locally.** Every
  size budget holds on both, which is the three-ABI sweep doing its job across
  a compiler generation rather than just across architectures.

The 80/80 Unity result also confirms what the Etap 3 notes said: the suites are
fine, and the intermittent blocking is the developer machine's Application
Control and nothing else.
